CAESIUM 2.0.5 — TECHNICAL ARCHITECTURAL SPECIFICATION
======================================================

Target
------
Minecraft 1.21.11
Fabric client mod
Java 21+
Primary rendering API: OpenGL

Purpose
-------
Caesium is a client-side performance and rendering engine designed around stable frame delivery, bounded asynchronous work, efficient chunk processing, conservative rendering correctness, and predictable memory behavior.

The engine must not trade short-term throughput for unbounded queues, stale world state, render-thread bursts, or long-session memory growth.

1. FRAME SCHEDULING
-------------------
Background work is admitted according to frame pressure and workload urgency.

Priority classes:
  CRITICAL    - work required for the current frame
  VISIBLE     - missing or outdated visible geometry
  PREDICTIVE  - geometry likely to become visible soon
  MAINTENANCE - cleanup, compaction, and speculative work

Frame-critical work is never delayed behind maintenance work. Background budgets may expand gradually when the frame has sustained headroom and a real backlog exists, but every stage remains bounded.

2. CHUNK PIPELINE
-----------------
Authoritative flow:

  chunk data available
      -> rebuild request
      -> priority queue
      -> worker extraction / meshing
      -> bounded completion queue
      -> render-thread budgeted integration
      -> bounded GPU upload
      -> scene / section storage
      -> visible terrain

Workers do not publish completed terrain directly into the active scene. The render-thread completion drain is the single integration owner.

3. ASYNCHRONOUS CORRECTNESS
---------------------------
Every asynchronous section result is associated with:
  - section identity;
  - section revision/version;
  - current renderer/world generation.

A result is rejected if its section revision is stale or its world generation no longer matches the active world.

Retries are bounded and delayed. Immediate retry loops and unbounded resubmission are prohibited.

4. BACKPRESSURE
---------------
Backpressure is required at every stage that can accumulate work:
  - rebuild admission;
  - meshing queue;
  - completion queue;
  - render-thread integration;
  - GPU upload queue.

Queue depth alone is not enough. Queue age is also used so old visible work cannot starve behind continuous new work.

5. MESHING
----------
Section extraction and meshing execute away from the render thread where safe. Profiling must distinguish queue wait from actual extraction/meshing cost.

Optimization targets include repeated block/model lookups, quad decoding, render-layer decisions, lighting/AO work, vertex packing, and block-entity classification. Caches are permitted only when their invalidation across resource/world lifecycle events is correct.

6. GPU UPLOAD
-------------
GPU upload work is bounded by both elapsed time and transferred data. OpenGL synchronization fences protect staged regions from unsafe reuse.

Upload allowance may adapt to sustained frame headroom and backlog pressure. It must contract quickly when frame pressure increases. Integrated GPUs require conservative limits because CPU and GPU share memory bandwidth.

7. VISIBILITY
-------------
Visibility uses cheap early rejection and conservative culling. Frustum, distance, and occlusion information may be combined, but uncertain geometry remains visible.

False-positive visibility costs performance; false-negative visibility causes missing geometry. Correctness therefore takes priority over aggressive culling.

8. BLOCK ENTITY OPTIMIZATION
----------------------------
Block entities are classified as STATIC, DYNAMIC, or UNSUPPORTED.

STATIC:
  Caesium may own valid section-integrated geometry.

DYNAMIC:
  Minecraft's normal block-entity renderer remains authoritative.

UNSUPPORTED:
  Conservative fallback to Minecraft rendering.

Static ownership must be invalidated on relevant block/entity state changes, section rebuilds, chunk unload, world replacement, resource/model reload, and animation transitions.

Current optimization work includes chests, signs, beds, bells, and campfires.

9. MEMORY
---------
Renderer-owned state must be bounded and lifecycle-managed. Hot paths may use primitive collections, packed structures, reusable buffers, pools, and native/off-heap memory when measurements justify them.

Native memory is explicitly owned and released. Teleports, rebuild storms, world changes, and long sessions must not cause monotonic renderer memory growth.

10. MULTIPLAYER
---------------
Caesium does not control server terrain generation or network delivery. Multiplayer performance must distinguish server/network delay from client chunk-to-visible latency.

No renderer optimization should fabricate, delay, or modify gameplay packets.

11. SINGLE-PLAYER
-----------------
The integrated server shares CPU resources with renderer workers. Worker concurrency must preserve server generation throughput. Increasing renderer worker count is not automatically an optimization.

12. TELEMETRY
-------------
Profiling should expose, with negligible disabled cost:
  - pending jobs;
  - active workers;
  - queue depth and oldest age;
  - meshes completed per second;
  - extraction/meshing time;
  - completion queue depth;
  - integration time and wait;
  - upload bytes/time/wait;
  - retries, deferrals, rejections, and stale discards;
  - client chunk-to-visible latency;
  - frame time, 1% lows, 0.1% lows, and worst frames.

13. CURRENT PERFORMANCE TARGET
------------------------------
The current 2.0.5 baseline has stable gameplay frame pacing in present testing. The remaining reproduced issue is slow chunk throughput in multiplayer and single-player.

The next optimization pass must identify the limiting stage before changing concurrency or budgets. The desired result is faster chunk appearance with the same frame-time stability.

14. SUPPORT BOUNDARY
--------------------
Supported public target:
  Minecraft 1.21.11
  Fabric
  Client side
  Java 21+
  OpenGL

Experimental or historical Vulkan, Java 25-only, NeoForge, or alternate-backend designs are not part of the supported current architecture unless a tested implementation exists in the current source tree.
